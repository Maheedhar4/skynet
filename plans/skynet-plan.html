_skynet_ — Plan

A Claude-style local chat app whose main feature is connecting to the Zepto quick-commerce MCP server and using it from chat. Status shown as a green light after a successful connect.

Stack

Frontend: Angular (standalone components) Backend: Node + TypeScript (Express) Model: Gemini via Google ADK TS (google/adk-js) — free-tier API key MCP: official @modelcontextprotocol/sdk client Monorepo: npm workspaces (apps/web, apps/server)

Research findings (verified live)

  • Zepto MCP is a remote hosted Streamable HTTP server: https://mcp.zepto.co.in/mcp — nothing to install locally.
  • OAuth discovery works: resource metadata at /.well-known/oauth-protected-resource → authorization server https://auth.zepto.co.in, which supports dynamic client registration, PKCE (S256), authorization_code + refresh_token.
  • Login is a browser flow: Indian mobile number + OTP (this is Zepto's "SSO").
  • Whitelisted OAuth redirect URIs: http://localhost, http://localhost/callback, http://127.0.0.1, http://127.0.0.1/callback — no ports listed.
  • Scopes include tools:read, tools:write, cart/order/checkout management (dev.ucp.shopping.*).
  • Tools exposed: Search Products · Cart Management · Order Placement · Order History. Orders placed via MCP are real orders (real money).

1 · Chat UI (Angular)

  • Claude-like message list + chat bar; responses stream in (SSE / ReadableStream).
  • Tool-activity chips inline, e.g. 🔍 Zepto search "amul milk" while a tool runs.
  • Header button: Connect to Quick Commerce MCPs, with a connector card per provider (Zepto now; Blinkit/Instamart later — config-driven registry).
  • Status dot per connector: disconnected → awaiting login / reconnecting → connected (handshake + tools/list succeeded).
  • Each card has a Disconnect action and a last-checked time.

2 · Zepto connect flow (backend)

  1. User clicks Connect → backend fetches resource metadata → discovers auth.zepto.co.in.
  2. Dynamic client registration at /register, then opens browser to Zepto authorize page → mobile number + OTP.
  3. Redirect lands on our /callback (backend) → exchange code with PKCE → store access + refresh token under ~/.skynet/ (file perms 0600).
  4. Complete MCP Streamable HTTP handshake → tools/list → status turns .
  5. Disconnect = call Zepto /revoke + clear tokens.
  6. On app restart: silent reconnect via refresh token — straight to if the token is valid.

3 · Chat ↔ Zepto tools (confirmed scope: "ask before ordering")

  • Search · cart view · order history: run directly, no confirmation needed.
  • Order placement & checkout (order:manage, checkout:manage scopes): backend intercepts, pauses the agent, and shows a prompt like "Zepto wants to place this order (₹542) — reply YES to confirm"; the tool fires only after the user confirms in chat.
⚠️ Real money: every order placed through Zepto MCP is processed as a real Zepto order. The confirmation gate is non-negotiable in v1.

4 · The chat brain (Google ADK)

  • ADK TS agent (@google/adk) with Gemini + Zepto MCP tools wired in; streams tokens to Angular.
  • Fallback guarantee: ADK TypeScript is new (0.x). If it's missing a capability we need (e.g. streaming, custom confirmation interception), fall back to a direct @google/genai function-calling loop using the same MCP-derived tools — the core experience doesn't break either way.
  • Requires GEMINI_API_KEY in .env (Google free tier).

Key technical decision / risk

OAuth redirect port problem: Zepto whitelists http://localhost and http://localhost/callback with no ports, and OAuth usually does exact-match on redirect URIs. So our callback must serve on port 80.

  • Primary: bind the Node backend's /callback on port 80 (one-time Linux privilege tweak: setcap/authbind/sudo, or iptables REDIRECT → documented in README).
  • First test during build: whether Zepto ignores the port (RFC 8252 loopback behavior). If it does, we stay on a normal port.
  • Both paths are covered in the plan; no dead end either way.

Other risks

  • ADK TS 0.x immaturity → fallback loop (above).
  • Free-tier Gemini rate limits → acceptable for MVP chat.
  • Token security → tokens stored in ~/.skynet/ with 0600 perms; never in the repo; refresh token used silently.
